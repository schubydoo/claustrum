`git.worktree_create` now picks the start commit for `sourceBranch` the way reference build `f6010b97` does. Three parts close older gaps, where `90fca6e6` and `f6010b97` agree and claustrum differed. The daemon now also reads `refs/remotes/origin/<sourceBranch>`. It takes that commit when the local branch is missing, points at a missing object, equals it or is behind it. It accepts revision syntax such as `feat~1`. On a detached HEAD it omits `sourceBranch` when `sourceBranch` is omitted. The next three parts are the `f6010b97` changes. The daemon passes the chosen commit id, so the new branch's reflog reads `Created from <sha>`. It takes the origin commit when the local branch changed the repo-root `.claude` or `.mcp.json`, in any letter case, since the merge base. It also takes the origin commit when there is no merge base, or when that diff fails. A failed checkout now fails the request with `git worktree add failed (checkout): …` and rolls back, where before it answered success without the checked-out files. That frame matches `90fca6e6`, and the `f6010b97` frame adds git's graft-file hint lines. When the caller's `timeoutMs` expires, the worktree is now rolled back, so a retry at the same path succeeds. The deadline no longer kills `git worktree add` or the copy step, and the reply waits for them. A copy step that outlives the deadline now answers `timeout` instead of success. A checkout that the deadline kills now quotes git's stderr when there is some. Every git text in these failure frames now keeps stderr only and its first 512 bytes. Invalid UTF-8 is dropped, each non-printable character becomes one space, and the text is trimmed. An empty text gives the exec error. An add that fails after the deadline now answers `worktree_add_failed` with git's stderr, not `timeout`. A checkout drain that outlives the deadline now runs the copy step first, and its rollback keeps `.git/worktrees/`. Both references agree on these timeout rules. When the attach to `existingBranch` fails, the daemon now creates `branchName` at the resolved `sourceBranch` commit, or at HEAD, and goes on. Both references do this. One cause is that baseRepo has that branch checked out. It skips that fallback when the failed attach add deleted or replaced the new directory. A failed add now runs no git call and removes the new directory only when it is empty and its parent was not replaced. A rollback that cannot delete a file now appends the references' undo text, and a failed first step keeps the registration and the branch. The checkout now runs inside the new directory with the git dir of baseRepo and a temporary index, as both references do. A `worktreePath` that ends in `/` now creates the worktree, where before the create failed with `file exists`. The success reply and the undo texts quote that path as sent. With `worktreeRoot`, the directory tests and the `already exists` refusal use the cleaned path, as both references do.
