# git.worktree_create

`git.worktree_create` makes a linked git worktree for a session. It creates a new branch, or attaches the worktree to one that exists, then checks out the tracked files and copies some ignored files into it. [After a failure](#after-a-failure) lists what a failed create leaves.

An untagged rule on this page matches the reference as measured on `5fd08069` or on an earlier build.

## Request

```json
{"baseRepo": "/repo", "branchName": "feature", "worktreePath": "/repo/.claude/worktrees/w1"}
```

| Parameter | Required | Meaning |
|---|---|---|
| `baseRepo` | yes | The repository. |
| `branchName` | yes | The branch to create. It is required with `existingBranch` too. An attach that succeeds does not use it. |
| `worktreePath` | yes | The directory of the new worktree. It must not exist. |
| `sourceBranch` | no | The name that the new branch starts from. The default is the current branch. An attach does not use it. |
| `existingBranch` | no | A local branch to attach to. If it names no local branch, or the attach fails, the daemon creates `branchName` instead. |
| `worktreeRoot` | no | A location outside the repository. Windows refuses it with `unsafe_path` and `` refusing to create worktree: `<root>` cannot be used: a custom worktree location is not supported on Windows hosts yet `` (`c9125eb8` and `4c111e86`, measured on Windows). |
| `timeoutMs` | no | A deadline that starts before the first git call. It stops the read-tree call, and [the content check](#the-content-check) at a step that sees it. The daemon tests it after the add and the copy step. The stop of the settle step from that start is measured (`683cc6a9`, Linux). For the other tests that start is claustrum's own, not measured. A wait at the add behind another create of the repository counts (claustrum's own, not measured). No value or `0` sets none. |
| `shadowDirOff` | no | `true` turns off, for this request, the filter rule of the checkout, the daemon's own read of the repository's git config, the settings copy and the content check. Git requests that start meanwhile get the same. A command that starts meanwhile gets no copy (measured on Linux). Other values do nothing. |

Where the worktree can go:

- Without `worktreeRoot`, `worktreePath` must be an absolute path inside `baseRepo`. The usual place is `<baseRepo>/.claude/worktrees/<name>`.
- With `worktreeRoot`, `worktreePath` must be `<worktreeRoot>/<directory>/<name>`. A root that exists must belong to the user of the daemon. Its mode must have no write bit for others, or for a group other than the private group of that user.
- Neither a component of the location nor the `<directory>` can be `.git` or `.claude-managed-worktrees`, in any letter case. The location must not resolve to `/`. It must not lie in a folder with a `.git` entry, the git directory of the repository, or the folder of a Claude Code session. The `<directory>` level must not hold the repository or be writable by every user.
- Not measured on the reference: `.claude-managed-worktrees` in the location, a reserved `<name>`, and the owner and group tests of the `<directory>` level. claustrum refuses all of them.

## Response

Success:

```json
{"success": true, "path": "/repo/.claude/worktrees/w1", "sourceBranch": "main", "branch": "feature"}
```

`path` is `worktreePath` as sent, after the `~` expansion. `branch` is `existingBranch` after an attach, and `branchName` otherwise.

If the daemon created a branch, `sourceBranch` is the name that the start commit came from. The daemon reads that name as two refs: the local branch `<name>` and the remote-tracking ref `origin/<name>`. It fetches nothing. If both exist, it selects `origin/<name>` in most states. The response holds the name as sent. If the name matches neither ref, the branch starts at HEAD with no error, and `sourceBranch` is the current branch. On a detached HEAD the response then has no `sourceBranch`.

Failure:

```json
{"success": false, "error": "<text>", "errorCode": "<code>"}
```

Decide by `errorCode` first.

| `errorCode` | Meaning |
|---|---|
| `unsafe_path` | The daemon refuses a path. For example, `worktreePath` is relative, has a `..` component, is outside `baseRepo`, or exists. An unsafe `worktreeRoot` and a worktree that git registered in an unexpected place give this code too. |
| `symlinked_component` | A directory between `baseRepo` and the worktree is a symbolic link. |
| `not_a_repo` | `baseRepo` is not a git repository, as with `refs` 0600 (`52d82f0a`, Linux and macOS), or git does not accept it. A bare `baseRepo` gets this code too while the daemon works on its settings copy. |
| `git_not_found` | No git on the daemon's PATH and none that it uses on the login shell's PATH ([the git of the login shell's PATH](git-rules-calls.md#the-git-of-the-login-shells-path)). The text is `not a git repository` (`87375cc7`, measured on Linux and macOS, and on Windows for a missing `baseRepo`). `4c111e86` answers `not_a_repo`. An existing `baseRepo` on Windows is claustrum's own. |
| `git_lfs_not_found` | Linux: the git of the login shell's PATH runs, and the checkout fails for a git-lfs that is on the login shell's PATH but neither beside that git nor on the daemon's PATH. The stderr of the checkout holds `git-lfs: not found` (measured with dash as `/bin/sh`). With bash as `/bin/sh` the create answers `worktree_add_failed` (claustrum's own, not measured). The text is `not a git repository`, and one line names the text of the checkout (`87375cc7`, measured on Linux). The undo of a failed checkout that comes first is claustrum's own, and its text can follow `not a git repository`. The words "neither beside that git" come from the log text, not measured. With git-lfs on no PATH the checkout failure stays. macOS gives `worktree_add_failed` (measured). |
| `nested_base_repo` | `baseRepo` is inside a directory of managed worktrees ([the marker rule](git-list-branches.md#response)), or is no trust root of the daemon. A marker above the path as sent counts too (`b3081b51`, measured on Linux). A missing `baseRepo` gets `not_a_repo` with no [start test](git-rules-settings-copy.md#the-start-test) (`4c111e86`, measured on all three systems), and a later Windows create makes no git call. Every other missing cause, such as `<T>/missing/..` on Linux and macOS, is claustrum's own. So are no `git version` call on Linux and macOS and the early answer to `"shadowDirOff":true`. On Windows `<out>\J\..\repo` (J a junction), `<T>\missing\..` and `<T>\t.txt\..` pass as the folder that `..` leaves, and the create makes the worktree there ([the walk](git-worktree-remove.md#where-the-paths-can-be), `b3081b51`, measured on Windows). A refused daemon count [answers first](git-rules-calls.md#where-each-method-answers-the-refusal) (from the code). |
| `mkdir_failed` | The daemon cannot create a directory for the worktree. Or, with `worktreeRoot`, a git call or a `.git` test failed first. |
| `worktree_add_failed` | `git worktree add`, the checkout or the `config.worktree` step failed. The text holds the message of git, or a refusal of the daemon before the add. A `git worktree add` that runs 2 minutes is stopped. |
| `repository_only_filter` | The checkout needs a git filter that only the git config of the repository defines. See [Git filters](#git-filters). |
| `timeout` | The deadline of `timeoutMs` expired. |
| `worktree_no_space` | A write of git-lfs in [the private LFS store](#the-private-lfs-store) met a full disk. |
| `worktree_quota` | A write of git-lfs in the private LFS store met a used-up disk quota. |
| `worktree_lfs_not_kept` | The deadline of `timeoutMs` expired during the checkout after a long copy into the private LFS store, or after Git LFS downloads began with a downloaded file that cannot be kept. |
| `worktree_lfs_no_space` | A Git LFS download left under a tenth of the free space at the start, and the daemon stopped the checkout. |
| `worktree_verify_content` | A file of [the content check](#the-content-check) does not match the commit, or is not executable though the commit records it so. |
| `worktree_verify_link` | A committed link of the content check leads to the top of the new worktree, runs in a circle, or passes through `/proc` or `/dev/fd`. |
| `worktree_verify_retry` | A file of the content check cannot be read, or git cannot hash the commit for the content check. |
| `worktree_verify_other_writer` | A file of the content check is in the new worktree but not in the commit. |
| `worktree_verify_repository` | git cannot read an object of the commit for the content check. |

A git config of the repository that the daemon does not accept gives `worktree_add_failed`, and nothing is made ([the texts](git-rules-config.md#repository-config-refusals)). Three settings copy failures do the same: a failed host git test, a failed call about the repository, and no copy folder.

## Error texts

Each text is in `error`, unless the row names a JSON-RPC error. The shared texts are in the [error-string catalogue](errors.md#error-string-catalogue). A row with no mark holds a text of the reference, measured on Linux. A mark such as "measured on macOS" limits its sentence to that system. A sentence that names systems without "measured" holds on each one.

## The main steps

A create records the git directory of `baseRepo` as a [session
folder](git-rules-session-folders.md#a-create) after `rev-parse --absolute-git-dir`.

```mermaid
flowchart TD
    A["gate"] --> C["git worktree add"] --> E["config.worktree step"] --> F["checkout"] --> H["content check"] --> G["copy of ignored files"]
```

## The held git directory

In the state `shadow` a create holds the git directory of `baseRepo` open from its gate to its reply. The gate is the trust check of the git directory and the daemon's own read of its config.

- The git directory must be a folder at the gate (claustrum's own test), also one with `IO_REPARSE_TAG_PROJFS` on Windows ([reparse tags](git-rules-windows-paths.md#a-folder-with-a-reparse-tag-that-is-no-link)). On Windows a junction or a directory symbolic link there is refused, on every git method without `"shadowDirOff": true`. With that member both link kinds pass, and git works behind the link. A request that starts during such a request gets this rule until its later gate (from the code, not measured). On Linux and macOS a `.git` that is a symbolic link before the request is resolved, and the daemon holds its target. With `"shadowDirOff": true` git answers its target, and the create succeeds (claustrum's own, not measured).
- The daemon's own deletes, renames, new folders and file writes inside the git directory go through the held folder. A folder put at the path during the create gets none of them, except the one the hold moves to ([Rare states](#rare-states)) and the Windows stale step.
- These go by the path: git itself, a host in the state `fallback-git` or with no run folder, and a request with `"shadowDirOff": true`. So does a request that starts while such a request runs, until a later gate before its first good add (claustrum's own). On Windows the stale-registration step goes by the path too, also behind a junction or a directory symbolic link put at `.git` right before `rev-parse --absolute-git-dir`. The link is not measured. On Linux and macOS the stale step goes by the path before that gate, or with a `worktrees` folder outside the held folder (from the code).

## The staged add

In the state `shadow` git adds the worktree in a short-lived folder of the daemon. The daemon then moves the registration into `<git dir>/worktrees` (`be1c1ca5`, measured on Linux, macOS and Windows).

- The `worktree add` call gets `GIT_COMMON_DIR=<S>/.s<n>` as its last entry (`4c111e86`, measured on Linux for an add with `-b`) and the path `<S>/.s<n>/leaf/<name>` (measured on Linux and Windows). `<S>` is the folder of the daemon. That copy holds no link `worktrees` (measured on Linux). A daemon `GIT_COMMON_DIR` does not stop the staging on Linux and macOS (`4c111e86`, measured). The add then ends with `GIT_OBJECT_DIRECTORY=<that folder>/objects` and `GIT_COMMON_DIR=<S>/.s<n>`, in this order, and gets the swap and `worktrees` refusals of a staged add (claustrum's own, not measured). On Windows `4c111e86` and `87375cc7` register the worktree in `baseRepo` and succeed (measured on Windows). claustrum stages that add as with no variable there ([the Windows rule](git-rules-trust.md#the-daemon-variables-on-windows)).
- In `.s<n>` the daemon makes `HEAD`, `config` and `info/exclude` with mode 0666 and `info`, `objects` and `refs` with 0777, less the umask. `.s<n>`, `worktrees` and each entry get 0700, and the files of an entry 0600 (`4c111e86`, measured on Linux under umask 022). The daemon makes no `leaf`: git makes it at the add, with 0755 (measured on Linux). macOS and Windows are claustrum's own.
- Before the add, `.s<n>` gets a folder `worktrees/<name>/reftable` for each registration with a `reftable` folder (`b3081b51`, measured on Linux). claustrum copies `tables.list` and each table that it names there (claustrum's own, not measured).
- A named table that is a link out of the git directory or missing refuses the create (measured on Linux and Windows). So does a named table that is a link inside it (claustrum's own, not measured). So does a `reftable` link (a junction on Windows) to a folder outside the git directory (measured on Linux and Windows). So does a FIFO as `tables.list` (measured on Linux). A named table that is no regular file and no link, such as a FIFO, gets `"<table>" is not a regular file`. A table name `.`, `..` or one with `/` or `\` gets `"<table>": invalid argument`. On Linux and macOS a link at `reftable` or `tables.list` that stays inside the git directory passes. These three are claustrum's own, not measured.
- A folder or a table in `reftable` that the list does not name and a `reftable` that is a regular file pass (measured on Linux).
- An empty `commondir` in the entry of another worktree passes, and the create succeeds (`4c111e86` and `c9125eb8`, measured on Linux). claustrum gives that file no copy in `.s<n>` (claustrum's own).
- A `HEAD` of up to 4096 bytes in the entry of another worktree gets a copy in `.s<n>`, and one of 4097 bytes or more gets none. The create succeeds (`4c111e86`, measured on Linux). macOS and Windows are claustrum's own.
- A `gitdir` of mode 000 in the entry of another worktree still gets a `gitdir` file in `.s<n>`, and the create succeeds (`4c111e86`, measured on Linux). Its text is not measured: claustrum writes an empty file. macOS and Windows are claustrum's own.
- After a good add the daemon copies the registration into `<git dir>/.claude-new-worktree-<16 hex>`. It renames that folder to the first free name of `<name>`, `<name>1` to `<name>99` in `worktrees` (measured on Windows, claustrum's own elsewhere). Git chooses `<name>`: a leaf `b ` with a trailing blank gets `b-` (measured on Linux). `b3081b51` copies an `info/sparse-checkout` of 4 MiB whole (measured on Linux). claustrum has no bound (claustrum's own, not measured above 4 MiB).
- On Linux and macOS a `worktrees` folder gone right after the add is made again (`4c111e86`, measured), with mode 0777 less the umask (`87375cc7`, measured on Linux, macOS claustrum's own, not measured). A failed mkdir there ends the create with its error (claustrum's own).
- Until the entry is complete it holds `locked` with `initializing` and a newline. The daemon writes the `.git` file of the leaf, which names the entry, and then removes `locked`.
- The `gitdir` record names `<leaf>/.git`, with the links of the path resolved and a trailing blank kept (measured on Linux). claustrum writes it (claustrum's own).
- The entry has no `logs` folder (measured on Linux and macOS).
- On Linux, in a `--shared=group` repository with a `worktrees` folder of mode 2775, the entry gets 2775 and the group of `worktrees`, and its files 664 with that group. On macOS the entry gets 755 under umask 022 and 775 under umask 002 (`b3081b51`, measured on macOS). It gets the group of `.git`, with no set-group-ID bit. Claustrum's own: each file keeps git's mode, and on Linux the entry keeps it and takes the group of a set-group-ID `worktrees`. On Linux the daemon makes the staging folder with mode 0777 less the umask (`87375cc7`, measured on Linux), and then gives it the mode of its source. On macOS the daemon makes the entry with mode 0775 less the umask (claustrum's own, other umasks not measured).
- On Windows a held staging folder or a held `locked` file gets 2 s of retries, also past `timeoutMs` (claustrum's own). A `locked` file held 1 s passes, and one held 3 s fails (measured on Windows).
- On Windows a create whose staged leaf folder or its parent folder another process holds open completes (`b3081b51`, measured on Windows). Access denied takes that path too. A `.git` there that is a link or over 8192 bytes, and a leaf folder that is a link or a junction, get the different-entry refusal (claustrum's own, not measured).
- A failed write of the `.git` file of the leaf, and a rollback, remove the moved registration by name. `config.worktree` and the index are new files there.
- With `"shadowDirOff": true` and in the state `fallback-git`, git adds the worktree at its own path.

## The settings copy

Git calls of the daemon read [a copy](git-rules-settings-copy.md#the-settings-copy) of the repository's settings. For this method:

- A missing `<git dir>/worktrees` is made before the add, with mode 0777 less the umask, and stays after a failed add. On Linux and macOS a last `core.sharedrepository` line of the copy other than `umask` sets its mode (`b3081b51`, measured on macOS). On macOS a `.git` group not the user's gives the folder no set-group-ID bit (`4c111e86`, measured on macOS). On Linux the folder keeps the bit only when it takes the user's group (claustrum's own).
- With `extensions.worktreeConfig` the new worktree gets the `config.worktree` file of `<git dir>`, or of a linked `baseRepo`, less `core.bare` and `core.worktree`.
- With `"shadowDirOff": true` the checkout has its index in `claude-ssh-checkout-<n>` of the temporary folder (`4c111e86`, measured on all three systems, the name only on Windows). The folder has mode 0700. `c9125eb8` names it `claude-ssh-index-<n>`.
- In the state `shadow`, the checkout has its index in [`.checkout-<n>`](git-rules-settings-copy.md#the-folders) (`4c111e86`, measured on all three systems). Two creates at once get two such folders.
- In the state `shadow` on Linux and macOS, the checkout uses [a private LFS store](#the-private-lfs-store).
- In the state `shadow`, a failed `rev-parse --absolute-git-dir` stops the create with `git worktree add failed: cannot locate the repository's git directory: exit status <n>`. Exit 128 is measured, and exit 1 on macOS. With `"shadowDirOff":true` exit 1 stops it (`4c111e86`, all three systems).
- In the state `shadow`, the `rev-parse --show-toplevel` pair runs before the add, unless an entry of `<git dir>/worktrees` names the leaf. An entry that the stale step removed does not stop the pair, which then comes after the listing of the add, right before the add (`c9125eb8` and `4c111e86`, measured on Linux). Its work tree is the resolved top of the repository, also for a `baseRepo` through a link (`4c111e86`, measured on Linux). With `"shadowDirOff":true` that row gives no pair (measured on Linux). macOS follows Linux (not measured), and Windows is not measured. One stale entry that stays for its `locked` file gives the listing of the add and the pair too, and then the locked refusal (`4c111e86`, measured on macOS). With `"shadowDirOff":true` it gives no pair (measured on macOS). Linux follows macOS, and Windows gives no pair there (not measured). A daemon `GIT_COMMON_DIR` gives no pair there (claustrum's own, not measured). A first create with no `<git dir>/worktrees` yet runs it too (`b3081b51` and `c9125eb8`, Linux, macOS and Windows). That pair comes at that place too (`c9125eb8` and `b3081b51`, measured on Linux and macOS, `87375cc7` in `shadow` on Windows). A link to a folder gives no pair (measured on Linux on `5fd08069`). `"shadowDirOff":true` with no folder gives no pair (`c9125eb8` and `b3081b51`, measured on Linux, and `87375cc7` on Windows, not on macOS). In `fallback-git` a create without that member runs the pair at the place of `shadow`, with a `<git dir>/worktrees` folder (`87375cc7`, measured on Windows). There a file or a junction at that path gives the pair too, and a missing folder gives none. On Linux and macOS it runs none there. These rules are claustrum's own, not measured. On Linux and macOS a refusal before the add then runs no pair (claustrum's own, not measured), except for [a swap after the listing](#rare-states). On Windows the pair comes before the refusals of the staging steps (claustrum's own, not measured). With the member outside `fallback-git` the pair gets [`GIT_SSH_COMMAND=false`](git-rules-calls.md#the-config-protocol-trace-and-ssh-names). With `worktreeRoot` the pair names `worktreePath` as its work tree (`c9125eb8` and `4c111e86`, measured on Linux, claustrum's own on macOS, not measured). For a linked `baseRepo` the pair names the main repository's `.git` in `--git-dir` (`4c111e86`, measured on Linux and macOS). On Windows its `--work-tree` is `baseRepo` with junctions and short names resolved. After a junction move right after `rev-parse --absolute-git-dir`, it is the leaf in the first repository (`87375cc7`, measured on Windows).
- With `worktreeRoot` in the state `shadow`, the light `rev-parse --show-toplevel`, the heavy `rev-parse --absolute-git-dir` and the light `worktree list --porcelain -z` run again. They follow the call about the repository after the add, and the settle step (`c9125eb8` and `4c111e86`, measured on Linux). An add of a commit id from `sourceBranch` runs them once more, and the call about the repository comes before the first `hash-object` call (`4c111e86` and `c9125eb8`, the call counts measured on Linux, for a folder whose `.git` is a broken link). Claustrum's own, not measured: their answers change nothing, other states run none, the place right after the add, and other shapes of `baseRepo`. A time-limit stop of one such call stops every later git call, so the checkout fails and rolls back. Claustrum's own, not measured: that stop in this round, and the first ask of such an add, which drops a bad answer. The content check asks again, so one bad answer that a second ask does not repeat no longer refuses with `worktree_verify_repository`.
- In the state `shadow`, an answer of `rev-parse --absolute-git-dir` that names another git directory gets one more call. After a right second answer the create succeeds. A wrong one stops the create with the prefix `git worktree add failed: cannot locate the repository's git directory: ` and the [disagree text](git-rules-settings-copy.md#the-call-about-the-repository), and the leaf does not stay (`c9125eb8`, measured on Linux and Windows). macOS, a failed second call, the root `baseRepo` as given in that text, and an answer with forward slashes on Windows are claustrum's own, not measured.
- On Linux and macOS, a linked worktree as `baseRepo` whose registration entry is a symbolic link gets the trust refusal after the prefix `git worktree add failed: cannot locate the repository's git directory: `, with the code `worktree_add_failed`. - A `.git` file to a missing path runs the [start test](git-rules-settings-copy.md#the-start-test), and in the state `shadow` the call about the repository, before the reply (`4c111e86`, measured on Linux and Windows, macOS claustrum's own). `4c111e86` runs `rev-parse --git-dir` once more there, with equal frames (measured on Windows). A failed call answers its text. Another answer with no error, other than "not a git repository", keeps the listing (claustrum's own). ## The private LFS store

In the state `shadow` on Linux and macOS, the read-tree call carries `lfs.storage=<.checkout-<n>>/lfs` (`4c111e86`, measured on Linux and macOS). Windows keeps `<git dir>/lfs`.

- Before the checkout, an object of `<git dir>/lfs/objects` is in that store when a pointer of the commit names it. It must be a regular file with the size of its pointer. On one file system it is a hard link, on another a copy (measured on Linux). A copy writes the object at its own name. A copy that stops at the deadline removes that one file at once, before the reply (measured on Linux and macOS). A copy that fails a write removes it too, and a link at `lfs` or `lfs/objects` gives a copy (measured on Linux). On an 8 MB file system (Linux) or a small disk image (macOS) the store gets no copy, and with 1100 MB (Linux) it does (measured). A copy needs the object size plus the larger of 1 GiB and a tenth of the size free. The first copy left out for the space ends the seed, so a later object gets no shard folder (measured on macOS with two copies. Linux, a later hard link and a later copy that fits are claustrum's own). An 11 GiB object is left out 1 MiB below that bound (measured on Linux and macOS). On macOS it is also left out at the size plus 1 GiB, 1 MiB either way, and copied 1 MiB above the bound (measured). A 200 MiB object needs about 1 GiB more (measured on Linux and macOS). A hard link needs no space (measured on macOS). The seed lists the commit with `-c core.commitGraph=false ls-tree --full-tree -r -l -z <id>` (measured on Linux, a pointer at the top of the tree). The same listing runs twice before `ls-tree`. `cat-file --batch --buffer` starts with `ls-tree`, before the first id, and reads the small blobs, with no listing before it. The calls of the seed run in `baseRepo`, with `GIT_DIR=<repo>/.git` and `GIT_WORK_TREE=<repo>` (measured on Linux).
### The keep

- After a good checkout, an object that git-lfs downloaded reaches `<git dir>/lfs/objects`. This keep runs after [the settle call](#the-settle-step), and the reply waits for it (`4c111e86`, measured on macOS). On Linux the object comes at the reply (measured), and the order after the settle call is claustrum's own, not measured. An object that the settle call put into the private store is kept too (claustrum's own, not measured). A link at `lfs` keeps nothing. The keep needs 1 GiB free plus the object size on the file system of that store, also when both stores share a file system (both measured on Linux and macOS). Without it only the empty shard folder stays (measured), and the exact byte is inferred. The rows fit a test after the checkout wrote its files, which is inferred. Missing shard folders get mode 0777 less the umask (measured on Linux). On macOS they got 0755 under the default umask (measured). macOS under another umask is claustrum's own. A missing `lfs` and `lfs/objects` get 0755 less the umask (claustrum's own). An object whose bytes and size differ from its pointer gets `lfs/objects` but no shard folder (measured on Linux and macOS). The keep also runs after a failed checkout, but not after the LFS space stop. After a deadline it keeps the object when the disk has the space. After a failed write of git it makes the shard folders (measured on Linux and macOS).
- A keep also runs every 2 s while the checkout runs (`4c111e86`, measured on Linux and macOS). In a row with two objects, the first reached the repository store 1.0 s after its download, while the checkout still ran. That fits the 2 s pass. The second came at the reply (`4c111e86`, measured on Linux). With 5 and 12 objects of 250 MiB each, all were there at the reply (measured on Linux). A keep that still runs at the exit of git stops there. A read of a 900 MiB object then ended with no copy, and only the keep after the checkout wrote a temp file (measured on Linux). On macOS the 3 s bound does not cut the copy of a tick (`87375cc7`, measured). With an 800 MB object 4 s before a 2 MB one, `87375cc7` kept the 2 MB object alone in 0 of 40 runs (measured). In the traced runs each object got one bytes test of at most 3.0 s, with no cut and no retry (`87375cc7`, measured). Claustrum's own, not measured: no 3 s bound on the bytes test of a tick, a keep as after a deadline, with no sweep, a stop during a copy on Linux and during the copy of a tick on macOS, no pass at time zero, and the rest of the keep on macOS.
- After a good checkout and after a deadline the keep copies the object, also on one file system (`4c111e86`, measured on Linux). It writes `.claude-<8 hex>-<oid>` in the shard with mode 0666 before the umask, in 32 KiB writes with no fsync. Then it links that name at `<oid>`. A `.kept-<oid>` link of the kept object then replaces the downloaded copy in the private store, and the temp name goes. A write that fails with `no space left on device` closes the file and removes it at once. No `.kept-` name is made, nothing is kept, and the reply stays a success. A 900 MiB copy stopped the same way 3.0 s after its second open, with `timeoutMs` 6500 to 10500 ms. A keep that ran past `timeoutMs`, kept or stopped, still answered success. - Then the shard of that object loses stale names `.claude-<8 hex>-<oid>`: those of the same oid, and others older than 10 minutes. ## Git filters

In the state `shadow`, a checkout that needs a filter that only the repository config defines, with a value that does not pass, fails the request. The texts are in [Error texts](#error-texts).

In the state `fallback-git` git runs the filters, and this section does not apply. In the state `shadow`:

- A filter is defined where its `smudge` or `process` key has a value. A file that the repository config includes counts as that config, also through `includeIf`, whatever its condition. With a settings copy, a last `smudge` or `process` line with no `=` in .git/config is a definition too.
- A filter of the user or system config or of the daemon environment runs with its values, also if the repository defines it. With a settings copy, an outside `process = cat` is no outside definition, so a repository `smudge` command is refused.
- With a user `lfs.storage` the checkout gets no `lfs.storage` item of the daemon (Linux, macOS and Windows). A failing user `smudge` fails the request where the repository adds only `required = true`, `yes` or `1`.
- Three repository values pass: `smudge = cat` under each name, and `git-lfs smudge -- %f` and `git-lfs filter-process` under `lfs`. With a settings copy `git-lfs smudge --skip %f` passes under `lfs` too. A filter whose values are all `cat` gets no item. With a settings copy, a name with `=` and `smudge = cat` succeeds (`4c111e86`, measured on Linux, macOS and Windows, on Linux and macOS also with a `.gitattributes` that names it). With a settings copy a bare `smudge` line or a value that does not pass (measured with `tr a b`) keeps the refusal (measured on Linux and macOS, claustrum's own on Windows). With no settings copy it stays too (claustrum's own, not measured).
- With a settings copy, a `smudge` value that does not pass refuses the filter, in .git/config or in an `includeIf` file, in either order. In .git/config only the last value counts. A plain include file and `config.worktree` count the same way (not measured).
- With a settings copy, a refused name that is not valid UTF-8 gets success on Windows. On Linux it gets the checkout text of git less those bytes.
- With a settings copy, a repository-only `lfs` filter with the `git lfs install` lines gets those lines as items. For such a filter a `required` value other than `true` goes as it is (claustrum's own, not measured). A user `clean = git-lfs clean -- %f` gives the `clean` item (claustrum's own, not measured). A `--skip` smudge in one repository file beside a git-lfs smudge in another passes (claustrum's own, not measured). A git-lfs program key of the repository refuses nothing, and its program does not run. With no settings copy such a key turns the filter `lfs` off (claustrum's own).
- A failed LFS checkout text can get a note about ssh, credential and proxy settings after it, or a note of [the private LFS store](#the-private-lfs-store).

The reap on macOS waits for the end of the check too. Windows gets one kill and reaps at the exit. Before the rollback on Windows, the check waits for each start under way and the exit of each killed helper, at most 3 s.
  - Also claustrum's own: after the kills, no commit, tree or file `hash-object` helper starts. If the scratch folder or the object write of a running helper fails then, one `hash-object --stdin` call still runs, with its call limit. A helper whose start was under way gets its kill at once, and so does a `cat-file --batch` that starts then. A `cat-file --buffer --batch` read gets none. After the kill, a `hash-object` that fails by itself writes no stop line. With a Git LFS keep, the kill comes at the deadline plus the keep time.
  - From the code: a check that saw the deadline kills the three long-running helpers before it closes their stdin. Another close comes at a malformed batch answer, at the end of a folder level for the tree helper, after a stopped `hash-object`, or at the end of a check that did not see the deadline. A helper that hangs after that close gets the kill with stdin closed.

## The copy of ignored files

After the checkout, the daemon copies two sets of files from `baseRepo` into the new worktree:

- The ignored files that the root file `.worktreeinclude` names. That file uses the syntax of `.gitignore`.
- The ignored files under `.claude/`.

Neither set includes `.claude/worktrees` or Claude's session state under `.claude/`, for example `checkpoints`, `mailbox` and `scheduled_tasks.json`.

Each copy is a new file with mode `0666` less the umask, not its source mode. The daemon skips symbolic links. A copy does not replace a file or a link that the checkout made.

A failed copy does not fail the request. If the deadline of `timeoutMs` expires during the copy, the request fails with `timeout`. After a content check that stopped at the deadline, the `.worktreeinclude` pass does not run (claustrum's own, not measured). A scan of ignored files stops at 10 minutes ([Time limits of git calls](git-rules-calls.md#time-limits-of-git-calls)). Then nothing is copied, the `.claude/` pass included (claustrum's own, not measured).

## After a failure

A request can create four things outside the worktree, and no failure removes them:

- directories above the worktree
- the registrations directory `<git dir>/worktrees`
- with `worktreeRoot`, the marker file `.claude-managed-worktrees` at the `<directory>` level
- with `worktreeRoot`, the folder of a gone worktree that holds the root

Before the add, a request can remove one stale registration in the common git directory of `baseRepo`. A stale registration is one whose `gitdir` record names the `.git` of the new worktree. If it is the one stale entry and has no `locked` file, it goes. Otherwise none goes. If the leaf is there at the stale step, none goes on Linux and macOS (claustrum's own, not measured). Nothing behind a symbolic link or a junction at `worktrees` goes (measured on Windows with `"shadowDirOff": true`, claustrum's own elsewhere). Two creates through a repository and its linked worktree add in turn. Two creates of one repository check out at the same time, and both download an object that neither had (`4c111e86`, measured on Linux). macOS and Windows are claustrum's own. A second create of one repository makes its git calls up to the add during the add of the first, then waits for it (`4c111e86`, measured on Linux). Claustrum's own, not measured: each rollback waits for such an add, so its reply can come later than `timeoutMs`.

After a good add in the state `shadow`, a create removes old staging entries of the git directory. Their name starts with `.claude-new-worktree-`, and their write time is 1 hour or more. A real folder goes as a tree. A link or a junction goes as a link, and its target stays. Measured on Linux, macOS and Windows, on Linux and macOS since `be1c1ca5`. The 1 hour edge and the name rule are measured on Linux.

| Failure | What stays of the worktree |
|---|---|
| A refusal of the request or of a path (`not_a_repo`, `nested_base_repo`, `symlinked_component`, and `unsafe_path` for a path) | Nothing, except the folder of a gone worktree above. |
| A refusal before `git worktree add` (`worktree_add_failed`), or `mkdir_failed` | Nothing. |
| `git worktree add` runs and fails (`worktree_add_failed`) | An empty worktree directory goes. Files, a registration and a branch that the failed add made stay. On Linux and macOS a file or a link that took the place of the directory goes too. A link goes as a link, and its target stays. The entry goes by its name through a handle of its parent folder: one unlink, then an rmdir if it is a folder. `c9125eb8` and `4c111e86` do so, measured on Linux with `"shadowDirOff": true`. macOS is claustrum's own, not measured. Windows keeps a file or a link (not measured). |
| A test of the new worktree fails after the add. On Linux and macOS, and on Windows with `"shadowDirOff": true`, the tests come before the checkout and give `unsafe_path`. A worktree directory replaced during the checkout gives `worktree_add_failed`. On Linux and macOS a replacing folder with no `.git` gets the `unsafe_path` text of a gone `.git` file instead (claustrum's own). So does a Windows test after the checkout. | Everything, except an empty worktree directory. In the state `shadow`, nothing stays for a `.git` file that names another staged entry or a `.git` that something put in the leaf. The worktree directory and the new branch go. On Linux and macOS a leaf moved away right after a staged add gets its `.git` file there. An empty folder at the path goes as after a failed add (`4c111e86`, measured). A folder with an entry and a link stay (claustrum's own, not measured). On Linux and macOS a leaf deleted and remade as an empty folder right after a staged add gets `worktree_add_failed` with the cause `openat .git: no such file or directory`. The moved registration, the branch and an empty folder at the path go (`4c111e86`, measured on Linux and macOS). A deleted leaf that is not remade gets the same cause and the same deletes, then the rmdir clause of the undo with `removeat <leaf base name>: no such file or directory` (`4c111e86`, measured on Linux). macOS is claustrum's own, not measured. A dangling link at the path, or a parent folder at the path that is not the one the create holds, keeps the error of the open of the leaf (claustrum's own, not measured). |

This test comes first, then the deadline test of the checkout (claustrum's own, not measured). | The registration and the branch. The worktree directory goes, except on Windows (`4c111e86`, measured). |
| The checkout or the `config.worktree` step fails, the filter rule refuses, or the deadline expires (`worktree_add_failed`, `repository_only_filter`, `timeout`), or the content check refuses (`worktree_verify_*`). Or the text holds `; retry` before any clause of the rollback (Linux and macOS). | The worktree directory, its registration and a branch that this request created go. |

??? note "When a rollback leaves something"

    - A branch with commits that no other ref reaches stays. The response has `"branchKept": true`.
    - After a failed `config.worktree` step, a refused second config read keeps the branch without `branchKept` (Linux and macOS).
    - A failed delete ends the error text with a clause that says what remains. If the files of the worktree cannot be deleted, the registration and the branch stay. A registration that cannot be deleted keeps the branch too, on Windows only for a moved registration (not measured on Windows). On Linux and macOS in the state `shadow`, after an empty answer of git about the git directory, a registration that cannot be deleted adds no clause, and the branch step runs (claustrum's own). On Windows a registration that stays adds no clause, unless the create moved it (not measured).
    - If something replaced the worktree directory after a good add, the rollback keeps the replacement and adds no clause.
    - On Linux and macOS a `.git` link right after a staged add keeps the new branch (claustrum's own, not measured), unless it names the held git directory (`4c111e86`, measured).

## Differences by system

=== "Linux and macOS"

    - A junction between `baseRepo` and the worktree does not apply.
    - The stale registration is removed by the rule of [After a failure](#after-a-failure). The compare keeps letter case.

=== "Windows"

    - A junction between `baseRepo` and the worktree is refused with `mkdir_failed`, also when a leaf exists behind it (`87375cc7`, measured on Windows).
    - A junction at `baseRepo` or above it passes. The worktree, its registration and the branch are made in the real repository. The `gitdir` record names the leaf with the junction resolved. After a failed checkout there, the leaf, the registration and the branch go (measured on Windows). A create that holds no git directory keeps the registration there (claustrum's own, not measured).
    - A `.git` file that names its entry through a junction holds the target of that junction (from the code).
    - A junction in `baseRepo` that moves to a second repository right after `rev-parse --absolute-git-dir`: the `worktree add` runs with that repository in `GIT_DIR`, and the branch lands there. The registration and the leaf land in the first repository. The reply is `` refusing to create worktree: `<worktreePath>` no longer leads to the directory that was created for the worktree `` with `unsafe_path`, with no checkout and no rollback (`4c111e86`, `87375cc7`, measured on Windows). The stale step does not run then. After a failed add the leaf rollback stops while the path leads to the second repository. With no checkpoint of the leaf (a nil `cp.info`) it runs one rmdir by path with no resolve test. After a move that can remove an empty folder in the second repository (all claustrum's own, not measured).
    - A junction in `baseRepo` moves to a second repository, and a read-tree call then fails by itself. The reply is `git worktree add failed (checkout): <git text>`, with no undo text. The leaf and the registration of the first repository go, and its new branch stays. In the second repository the ref of the same name goes, also for a live or locked worktree. Its entry, its empty leaf and its lock stay. With no such ref, nothing goes there (`87375cc7`, measured on Windows, 5 of 5). The maintainer approved this delete. A gate of the second repository that refuses keeps its ref, with the same reply (claustrum's own, not measured).
    - A junction in `baseRepo` moves to a second repository, or to a folder with no git directory, right before a read-tree call that succeeds. The calls of the checkout name the resolved leaf as their working folder and `--work-tree`, also with no move. So the tree lands in the leaf of the first repository, and the new target stays unchanged. The reply is `` refusing to create worktree: `<worktreePath>` no longer leads to the directory that was created for the worktree `` with `unsafe_path`. The leaf, its index, the branch and the entry of the first repository stay, with no rollback (`87375cc7`, measured on Windows, 12 of 12).
    - The stale registration goes by the same rule, after `rev-parse --absolute-git-dir`. The compare ignores letter case, measured for a create that holds its git directory. An entry whose record names a path that exists stays ([D27](../DIVERGENCES.md#d27)).
    - A rename of the staging folder that still fails after its retries gives `worktree_add_failed`.
    - An alternates file with Windows line endings or too many object directories gives `worktree_add_failed`, and nothing is made (from the code). [The object sources on Windows](git-rules-trust.md#the-object-sources-on-windows). A daemon `GIT_ALTERNATE_OBJECT_DIRECTORIES`: [Object sources](git-rules-trust.md#the-object-sources-on-windows).
    - A `baseRepo` through a link to a network or device path gives `worktree_add_failed`, and no git call runs. [A link to a network or device path](git-rules-windows-paths.md#a-link-to-a-network-or-device-path).
    - A `\\?\UNC\` `baseRepo` or a refused share gives `worktree_add_failed`. [UNC refusals](git-rules-windows-paths.md#unc-refusals).
    - A `.git` with `IO_REPARSE_TAG_WIM` gives `worktree_add_failed`, and no git call runs (`4c111e86`). [Reparse tags](git-rules-windows-paths.md#a-folder-with-a-reparse-tag-that-is-no-link).

## Rare states

??? note "When the git directory is replaced during a create"

    - In `shadow` on Linux and macOS three swaps move the hold, and the create goes on in the new folder. One is a link to a copy at `.git` after the first call or after `rev-parse --abbrev-ref HEAD`. Another is a real directory that passes the gate, put there while `git worktree add` runs or right after it, such as a copy or a second repository. The registration goes into it. `be1c1ca5` does the same, and its create succeeds for a copy (measured on Linux).
    - The third is a symbolic link to a copy at `.git`, put there right after `rev-parse --absolute-git-dir` answered. After the call about the repository, the read of the config and the listing, the daemon makes that call again. It goes on in the copy, and the create succeeds (`4c111e86`, measured on Linux). The record of the session folder names the copy. Its calls with `--git-dir=<copy>` then name a new folder of the copy in `GIT_COMMON_DIR` (`4c111e86`, measured on Linux). Its other calls that name a folder of a repository keep the first folder. A link to a second repository gets the same rule (claustrum's own, not measured). macOS follows Linux (not measured).
    - After that second move a rollback deletes the moved registration by its identity through the new folder. For a second repository whose checkout fails, `be1c1ca5` and claustrum both remove the registration there and keep the branch in the old folder (measured on Linux). The branch step after the move deletes only a branch with the tip that this call made, so a branch of the same name in the new folder stays (claustrum's own, `be1c1ca5` not measured in this state). A rollback after the first move is not measured.
    - In `shadow` a symbolic link at `.git`, put there while git adds or right after it, gives `git worktree add failed (completing the new worktree's git files): ".git" is a link or a file where Claude needs a real directory; put the directory itself in its place`, and the leaf goes (`be1c1ca5`, measured on Linux). For a link right before it, `be1c1ca5` deletes the branch through it. claustrum keeps it unless the link names the held git directory (claustrum's own, not measured, [D24](../DIVERGENCES.md#d24)).
    - In `shadow` any other swap after `rev-parse --absolute-git-dir` answered and before the add stops the add. On Linux and macOS a link to a copy at `.git` after the listing of the add gives `cannot add a worktree: cannot prepare the repository's worktrees directory: ".git" is a link or a file where Claude needs a real directory; put the directory itself in its place` (`4c111e86`, measured on Linux). A new read of the config and the pair come before that refusal. macOS follows Linux (not measured). A swap after the answer test and before that listing gets `git worktree add failed: ` (from the code).
    - In `shadow` on Windows four junctions give these texts (`b3081b51`, measured on Windows). A junction at `.git` right after `rev-parse --absolute-git-dir` gives `cannot add a worktree: cannot list the repository's worktree entries: ".git" is a link or a file where Claude needs a real directory; put the directory itself in its place`. A junction at `<git dir>\worktrees` there gives `cannot add a worktree: cannot prepare the repository's worktrees directory: "<git dir>\worktrees" is not a directory`. Right before the `worktree add` call, a junction at `.git` gives `git worktree add failed (completing the new worktree's git files): this repository's git config cannot be used: "<git dir>\config": is, or is reached through, a link that Claude does not follow here; replace the link with what it points to`, and the text of the rollback follows. A junction at `<git dir>\worktrees` there gives `git worktree add failed (completing the new worktree's git files): statat worktrees\w199: path escapes from parent`. A junction at `worktrees` that was there before the request gets its text after the listing of the add and the pair (`87375cc7`, measured on Windows). A directory symbolic link or another real directory at `.git`, any other link at `worktrees`, and any other Lstat error get these texts too (claustrum's own, not measured). After a junction at `.git` right before `rev-parse --absolute-git-dir` the reply is equal. The stale step then removes the entry of the folder behind the junction, as `b3081b51` does (measured on Windows).
    - In `shadow` a swap after the read-tree call fails the create with a text that starts `git worktree add failed (checkout): `. On Windows a swap after the first listing of the checkout does the same. The registration gets no index. It and the branch stay, and the text says so. The junction move to a second repository in the Windows list above is the exception.

??? note "A failed step before the add"

    - In the state `shadow` on Windows, a failed step that prepares the add (for example the read of the registrations, the folder `.s<n>` and its copy, or a swap of `.git`) gives `git worktree add failed: cannot prepare the repository's worktrees directory: <cause>`, except a file at `worktrees` ([Folder refusals](#folder-refusals)). No `worktree add` runs.
    - On Linux and macOS a failed read of the registrations or copy into `.s<n>` gives the same text (claustrum's own). A folder `.s<n>` that cannot be made gives its own text.
    - A failed copy of the refs gives its own text ([Staged add failures](#staged-add-failures)).

## Differences from the reference

Divergences of this method:

- [D2](../DIVERGENCES.md#d2): a delete refuses a path that is the home directory or holds it.
- [D24](../DIVERGENCES.md#d24): a rollback and the index placement leave a registration directory that something replaced. On Windows a rollback after a swap of the `.git` file of the worktree runs no git call. On Linux and macOS a rollback after a link at `.git` during the staged add deletes no branch through it, unless the link names the held git directory.
- [D27](../DIVERGENCES.md#d27): on Windows the stale step keeps an entry whose record names a path that exists.
